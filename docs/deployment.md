# Деплой

Прод-контур поднимается одним `docker compose` из корня репозитория. Образы
собираются локально: бэкенд из `backend/Dockerfile.prod`, фронтенд из
`frontend/Dockerfile` — там же он и собирается Vite, а результат кладётся в
образ nginx. Ничего никуда не публикуется.

## Что требуется

- Linux-сервер с Docker и плагином Compose
  ([инструкция](https://docs.docker.com/engine/install/)). Проверялось на
  Ubuntu Server 24.04 LTS; `server-setup.sh` ставит Docker сам
- От 2 ГБ оперативной памяти и 10 ГБ диска, а с мониторингом — от 3 ГБ и
  20 ГБ. Фронтенд собирается на сервере, и на машине с гигабайтом сборка
  падает по нехватке памяти. Контур настроен под четыре ядра и четыре
  гигабайта: столько же воркеров у бэкенда, под них посчитан пул соединений,
  под этот объём памяти заданы параметры PostgreSQL
- DNS-запись на IP сервера

## Развёртывание

```bash
git clone https://github.com/vomas7/location_king.git
cd location_king
./deploy.sh
```

Всё. Скрипт проверяет Docker, создаёт `.env` со сгенерированными паролями,
собирает образы, поднимает контур, дожидается здорового бэкенда, накатывает
миграции, загружает игровые зоны и стучится в `/api/health`. То же самое —
`make deploy`.

Обновление ничем не отличается:

```bash
git pull && ./deploy.sh
```

Переменные из `.env` можно передать и окружением — тогда правка файла
редактором не нужна вовсе, а значение запишется в `.env`:

```bash
NGINX_PROFILE=letsencrypt SSL_EXTRA_DOMAINS=www.example.com ./deploy.sh
```

Так задаются `SITE_URL`, `OPERATOR_NAME`, `OPERATOR_EMAIL`, `NGINX_PROFILE`,
`SSL_EMAIL` и `SSL_EXTRA_DOMAINS`. Пароли и секреты — только в файле.

Если бэкенд не поднимется за три минуты, скрипт покажет его логи и завершится
с ошибкой, а не пойдёт накатывать миграции в пустоту.

### Чистый сервер, три вставки

На сервере, где ещё нет ни Docker, ни репозитория, всё это делает
`server-setup.sh`. Он ставит Docker, забирает код в `/opt/location_king` и
передаёт дело `deploy.sh`. Рассчитан на то, что команды вставляют с телефона,
поэтому команда одна:

```bash
curl -fsSL https://raw.githubusercontent.com/vomas7/location_king/main/server-setup.sh \
    | sudo OPERATOR_NAME="Имя оператора" OPERATOR_EMAIL=mail@example.com bash
```

Реквизиты оператора уйдут в `.env` при его создании — потом их можно поменять
там же. Не передали — скрипт отработает и без них, документы просто скажут,
что контакт не указан.

Первый запуск остановится на origin-сертификате Cloudflare: скрипт напечатает,
где его взять, и две готовые команды. Вставьте сертификат и ключ, запустите ту
же строку ещё раз — дальше всё пойдёт само.

Закрытый ключ существует в одном экземпляре: он попадает на сервер только из
панели Cloudflare, минуя переписки и заметки.

## Автоматическое развёртывание

Ветка `deploy` — это «то, что можно ставить на сервер». Двигает её только CI и
только после того, как все проверки коммита стали зелёными. Сервер следит за
ней сам и забирает изменения к себе:

```
push в main  →  Backend CI · Frontend CI · E2E  →  ветка deploy  →  сервер
```

Таймер systemd раз в две минуты зовёт `autodeploy.sh`. Тот сравнивает
`origin/deploy` с тем, что развёрнуто, и если появилось новое — переключается
на него и запускает обычный `deploy.sh`.

### Почему сервер сам ходит за версией

Обратный вариант — GitHub подключается к серверу по SSH — потребовал бы
положить в настройки репозитория ключ с доступом к машине и открыть ей вход
снаружи. Тогда доступ к серверу получал бы каждый, кто может править файл
workflow или подменить чужой action.

Здесь наружу не открыто ничего, а ключей от сервера нет нигде, кроме самого
сервера. Плата за это — задержка до двух минут и отсутствие отметки о
развёртывании в интерфейсе GitHub.

### Если новая версия не поднялась

`deploy.sh` не считает развёртывание удавшимся, пока бэкенд не станет здоровым.
Не стал — `autodeploy.sh` возвращает предыдущий коммит и разворачивает его
заново. То есть неудачная версия оставляет игру работающей на прежней.

Не удался и откат — скрипт останавливается и пишет об этом в журнал: дальше
нужен человек.

### Как понять, что версия доехала

Сборка отмечает, из какого коммита она собрана, и отдаёт это файлом
`/version.json`:

```bash
curl -s https://locationking.ru/version.json
```

Значение сравнивается с веткой `deploy` — вручную или проверкой `Uptime`,
которая делает это каждые пятнадцать минут. Отставание в пределах получаса
считается нормой: сервер смотрит за обновлениями раз в две минуты, а сборка
фронтенда идёт несколько минут.

Без этой отметки молчащее автоматическое развёртывание выглядит как
работающее: снаружи вчерашняя сборка ничем не отличается от сегодняшней.

### Как за этим следить

```bash
systemctl status location-king-deploy.timer   # включён ли таймер
journalctl -u location-king-deploy -f         # что происходит сейчас
journalctl -u location-king-deploy --since today
```

Записи журнала уходят и в Loki, поэтому историю развёртываний видно в Grafana
рядом с логами игры — на дашборде «Логи» выберите контейнер `systemd`.

### Ручное управление

Развернуть немедленно, не дожидаясь таймера:

```bash
systemctl start location-king-deploy
```

Выключить автоматику совсем:

```bash
systemctl disable --now location-king-deploy.timer
```

Развернуть коммит, минуя ветку `deploy`, — например, чтобы срочно откатиться:

```bash
cd /opt/location_king
git checkout <коммит>
./deploy.sh
```

Следующее срабатывание таймера вернёт сервер на `origin/deploy`, так что после
ручного отката нужно либо выключить таймер, либо починить ветку в репозитории.

### Почему упавшая проверка доступности не блокирует выкладку

Список проверок в `Release` задан явно — Backend CI, Frontend CI и E2E.
Запуск по расписанию тоже привязан к коммиту, и проверка доступности иначе
попадала бы в те же ворота: сайт лежит, значит, выкладка запрещена. Ровно
тогда, когда выкладывать нужнее всего.

### Продвинуть версию руками

В GitHub: **Actions → Release → Run workflow**. Полезно, когда проверки
перезапускали вручную и автоматический запуск уже не сработает.

## Сервисы

| Сервис     | Образ                             | Сеть        | Назначение                        |
|------------|-----------------------------------|-------------|-----------------------------------|
| `nginx`    | сборка `frontend/Dockerfile`      | edge        | статика фронтенда и прокси к API  |
| `backend`  | сборка `backend/Dockerfile.prod`  | edge + data | FastAPI                           |
| `postgres` | `postgis/postgis:16-3.4-alpine`   | data        | основная база                     |
| `redis`    | `redis:7-alpine`                  | data        | кэш спутниковых тайлов            |
| `certbot`  | `certbot/certbot`                 | edge        | продление сертификата Let's Encrypt |

Плюс пять служб наблюдаемости — Prometheus, Loki, Alloy, node-exporter и
Grafana. Они поднимаются при `MONITORING=true` и описаны отдельно, в
[monitoring.md](monitoring.md).

`certbot` поднимается только при `NGINX_PROFILE=letsencrypt` — он объявлен
через `profiles`, и `deploy.sh` включает его сам.

Сеть `data` объявлена `internal: true`: база и кэш недоступны снаружи.
Бэкенд подключён и к `edge` — иначе он не смог бы забирать тайлы снимков.

Фронтенд и API отдаются с одного origin, поэтому CORS в прод-контуре не
используется вовсе.

## Что стоит настроить

Значения по умолчанию рабочие, но три вещи обычно правят руками в `.env`.

**Контур TLS.** Переменная `NGINX_PROFILE`:

- `letsencrypt` (по умолчанию) — сертификат выпускает и продлевает certbot,
  игроки приходят прямо на сервер. Отдельный раздел ниже;
- `cloudflare` — сайт стоит за Cloudflare, тот же раздел ниже;
- `tls` — сертификаты свои. Положите их в `./ssl` как `fullchain.pem` и
  `privkey.pem`; nginx поднимет 443, включит HSTS и будет редиректить с 80;
- `http` — сертификаты терминирует хостинг или балансировщик, nginx слушает
  только 80.

Файлов сертификатов не хватает — `deploy.sh` откажется продолжать, а не
поднимет контур, который не умеет отвечать по HTTPS.

**Адрес сайта.** `SITE_URL` в `.env`, по умолчанию `https://locationking.ru`.
Из него собираются `canonical`, `og:url` и `sitemap.xml`. Пусто — этих тегов
просто не будет: неверный `canonical` хуже отсутствующего, поисковик по нему
склеит не те страницы. Переменная уходит в сборку фронтенда аргументом, так
что после её смены нужен `./deploy.sh`, а не просто перезапуск.

**Реквизиты оператора.** `OPERATOR_NAME` и `OPERATOR_EMAIL` в `.env` — имя и
адрес того, кто отвечает за сервис. Они показываются в условиях использования
и политике конфиденциальности; пока поля пустые, документы честно сообщают,
что контакт не указан, а `deploy.sh` предупреждает об этом. Подробности — в
[legal.md](legal.md).

**Провайдер снимков.** `SATELLITE_TILE_URL` — см. раздел ниже.

**Прогрев кэша.** `TILE_PREWARM=false` выключает предзагрузку верхних тайлов
раунда: игрок будет дольше ждать первый экран, зато запросов к провайдеру
станет меньше.

Секреты `POSTGRES_PASSWORD`, `REDIS_PASSWORD` и `JWT_SECRET` скрипт генерирует
сам при первом запуске. Заполненные вручную значения он не трогает. Без
`JWT_SECRET` бэкенд не стартует — это сделано намеренно.

Конфигурация клиента (`config.js`) собирается в образе скриптом
`frontend/scripts/make-config.mjs` из тех же переменных `.env`. Версия из
репозитория — дефолт для разработки, править её на сервере не нужно: она
всё равно перезапишется при сборке.

Если нужно сделать шаг вручную:

```bash
docker compose up -d --build
docker compose exec backend alembic upgrade head
docker compose exec backend python scripts/seed.py
```

Остальные команды — в корневом `Makefile`: `make prod`, `make prod-down`,
`make prod-logs`.

## Сертификат Let's Encrypt

Контур по умолчанию: `NGINX_PROFILE=letsencrypt`. Игроки соединяются с
сервером напрямую, сертификат бесплатный и продлевается сам.

### Что нужно от человека

Только записи DNS, указывающие на сервер. Если домен обслуживает Cloudflare,
у записей должно стоять **серое** облачко (DNS only): с оранжевым проверка
Let's Encrypt уйдёт на серверы Cloudflare и до сервера не дойдёт.

Дальше всё делает `deploy.sh`. Домен он берёт из `SITE_URL`, адрес для
уведомлений — из `SSL_EMAIL` или, если тот пуст, из `OPERATOR_EMAIL`.
Дополнительные имена в том же сертификате перечисляются через запятую в
`SSL_EXTRA_DOMAINS` — например, `www.locationking.ru`. Каждое из них тоже
должно указывать на сервер: домен без записи в DNS завалит проверку целиком.

### Как это устроено

Проверка Let's Encrypt приходит по HTTP на 80-й порт, а nginx контура без
сертификата не стартует вовсе. Поэтому на время выпуска порт занимает
временный контейнер, умеющий ровно одно — отдать файл проверки из
`./certbot/www`. Способ проверки тот же, что и при продлении: иначе продление
отличалось бы от выпуска и однажды отвалилось бы молча.

Продлевает сертификат контейнер `certbot`: он просыпается раз в двенадцать
часов и обновляет то, чему осталось меньше месяца. Свежий сертификат
появляется в томе рядом с работающим nginx, а подхватывается только
перезагрузкой конфигурации — nginx перечитывает её раз в шесть часов сам.

Каталог сертификата фиксирован (`--cert-name main`), поэтому пути в
`nginx/letsencrypt/site.conf` не зависят от домена.

### Что за это платим

Настоящий адрес сервера виден в DNS, и защиты от нагрузки перед ним нет.
Взамен доступность не зависит от того, дотягивается ли сеть Cloudflare до
игрока: в России её периодически не видно.

## За Cloudflare

Альтернативный контур: `NGINX_PROFILE=cloudflare`. Браузер общается с
Cloudflare по обычному сертификату, Cloudflare с сервером — по
origin-сертификату, а настоящий адрес игрока приходит заголовком
`CF-Connecting-IP`. Прячет адрес сервера и снимает часть нагрузки, но
доступность сайта начинает зависеть от доступности самого Cloudflare.

### В панели Cloudflare

1. **DNS.** Запись `A` на IP сервера с включённым проксированием — оранжевое
   облако. Серое облако означает, что трафик идёт мимо Cloudflare, и весь
   этот раздел не работает.

2. **Origin-сертификат.** SSL/TLS → Origin Server → Create Certificate.
   Сохраните две части на сервер:

   ```
   ssl/origin.pem   — сертификат
   ssl/origin.key   — закрытый ключ
   ```

   Он живёт пятнадцать лет и доверяют ему только серверы Cloudflare — этого
   здесь и достаточно.

3. **Режим шифрования.** SSL/TLS → Overview → **Full (strict)**. В режиме
   Flexible Cloudflare пойдёт на сервер по открытому HTTP, и наш контур,
   слушающий 443, ему просто не ответит.

4. **Authenticated Origin Pulls.** SSL/TLS → Origin Server → включить.
   Cloudflare начнёт предъявлять серверу клиентский сертификат, а сервер —
   отказывать всем остальным. Без этого origin остаётся доступен любому, кто
   узнает его адрес и подставит нужный `Host`.

5. По желанию: Always Use HTTPS, Automatic HTTPS Rewrites, Brotli.

### На сервере

```bash
NGINX_PROFILE=cloudflare  # в .env
./deploy.sh
```

`deploy.sh` при этом сам:

- забирает актуальный список сетей Cloudflare с `cloudflare.com/ips-v4` и
  `ips-v6` и собирает `nginx/snippets/cloudflare-real-ip.conf`. В репозитории
  этого файла нет намеренно: захардкоженный список однажды устарел бы молча, а
  устаревший список опаснее отсутствующего — с ним nginx поверил бы заголовку
  `CF-Connecting-IP` не от Cloudflare;
- скачивает CA для Authenticated Origin Pulls, если его ещё нет, и включает
  проверку клиентского сертификата. Не получилось скачать — контур поднимется
  без этой проверки, и скрипт скажет об этом в вывод;
- проверяет, что `ssl/origin.pem` и `ssl/origin.key` на месте.

Оба собранных фрагмента перезаписываются при каждом развёртывании — правки в
них не сохранятся.

### Что с адресом игрока

Ограничение частоты запросов считается по адресу. За Cloudflare в
`X-Forwarded-For` бэкенду уходит **только** то, что Cloudflare подтвердил
заголовком `CF-Connecting-IP`; то, что прислал клиент, отбрасывается. Значит,
подделать чужой адрес и обойти лимит нельзя.

В контурах `http` и `tls` пересылается цепочка `X-Forwarded-For`, как её
собрал предыдущий прокси. Если перед сервером никого нет, доверять этому
заголовку нельзя — тогда используйте `cloudflare`.

### 400 No required SSL certificate was sent

Так nginx отвечает тому, кто пришёл мимо Cloudflare: Authenticated Origin
Pulls требует клиентский сертификат, а его присылает только Cloudflare. Если
эту страницу видно в браузере по адресу сайта, причина одна из двух.

**Запись DNS не проксируется.** В панели Cloudflare у записи `A` серое
облачко вместо оранжевого: Cloudflare отдаёт браузеру адрес сервера и в
соединение не вмешивается. Признак — браузер вдобавок ругается на сертификат:
он видит origin-сертификат Cloudflare, который не признаёт ни один браузер.
Проверить, что домен действительно проксируется, можно по адресу, в который он
разрешается: у проксируемого он из [сетей Cloudflare](https://www.cloudflare.com/ips-v4),
а не совпадает с IP сервера.

**Зональный тумблер выключен.** `deploy.sh` настраивает проверку сертификата
на стороне nginx, но включить отправку сертификата со стороны Cloudflare может
только владелец зоны: SSL/TLS → Origin Server → Authenticated Origin Pulls.
Тогда падают уже все запросы, включая пришедшие через Cloudflare.

## Расписание

Партии, брошенные посреди игры, остаются активными и мешают статистике.
Закрывать их стоит по расписанию, например раз в час:

```cron
0 * * * * cd /path/to/location_king && docker compose exec -T backend python scripts/cleanup.py
```

## Миграции

Применяются только вперёд; уже применённые ревизии не редактируются.
`deploy.sh` накатывает их сам после каждого обновления.

## Роботы и сканеры

Открытый в интернет сервер получает поток чужого внимания с первого дня:
переборы `wp-admin` и `.env`, попытки войти по чужим паролям, долбёжка по
адресам, которых у нас нет. Отдельного «взлома» для этого не нужно, поэтому
защита стоит слоями, и каждый слой дешевле следующего.

**Отсев на входе.** `nginx/snippets/site.conf` закрывает соединение без
ответа (код 444) на путях, которых в игре нет вовсе: панели чужих CMS,
забытые дампы, `.git`, `.env`, файлы с расширениями `.php`, `.sql`, `.bak`.
Сканер не получает даже кода, по которому мог бы отличить «нет такого» от
«есть, но закрыто». Методы, кроме шести используемых игрой, получают 405 и до
приложения не доходят.

**Ограничение частоты.** Зоны заданы в
`nginx/snippets/http-context.conf`: 60 запросов в секунду на игровые пути и
один в секунду на вход, регистрацию и обновление токена. Считается по адресу,
и за Cloudflare это настоящий адрес игрока — `real_ip` подставляет его до
того, как счётчик увидит запрос. Отказ отвечает кодом 429.

Это не заменяет счётчики приложения (`app/services/rate_limit.py`), а стоит
перед ними: приложение считает игровые действия и тратит на каждую попытку
Redis и обращение к базе, а здесь отсекается то, что до приложения доходить
вообще не должно. Перебор пароля упирается в nginx после десятой попытки, не
дойдя до argon2 — а именно argon2 стоит дорого, в том и смысл.

**Медленные соединения.** `client_body_timeout`, `client_header_timeout` и
`keepalive_timeout` не дают держать соединение открытым бесконечно: самая
дешёвая атака на веб-сервер — открыть сотни соединений и слать по байту в
минуту. `limit_conn` ограничивает сотней одновременных соединений с адреса.

**Размер тела.** Мегабайт на всё, кроме загрузки аватарки, — там пять.
Приложение при этом не полагается на nginx и само читает файл с потолком.

**Обход Cloudflare.** В контуре `cloudflare` origin принимает соединения
только из сетей Cloudflare: список собирает `deploy.sh` при каждом
развёртывании и кладёт в `nginx/snippets/cloudflare-only.conf`. Без этого
сканер, нашедший адрес сервера перебором сетей хостинга, обходит и защиту
Cloudflare, и подсчёт настоящего адреса игрока — одной строкой в `curl`.

Если вы обращались к серверу по адресу напрямую, после обновления это
перестанет работать: ходите через домен. Для отладки с самого сервера
остаётся `docker compose exec`.

`server_tokens off` убирает версию nginx из заголовка `Server` и страниц
ошибок: по версии сканер сразу подбирает список известных для неё дыр.

## Что стоит настроить на самой машине

Всё описанное выше живёт в репозитории и приезжает с развёртыванием. Хост
настраивается один раз и руками — вот необходимый минимум.

**Файрвол.** Наружу нужны только 80, 443 и порт SSH. Postgres и Redis портов
не публикуют вовсе, но правило лишним не будет:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
```

**Вход по ключу.** Пароль подбирают круглосуточно, ключ — нет. В
`/etc/ssh/sshd_config`:

```
PasswordAuthentication no
PermitRootLogin prohibit-password
```

и `sudo systemctl reload ssh`. Прежде чем перезагружать — убедитесь, что ключ
уже работает: иначе останетесь снаружи.

**Автоматические обновления безопасности.** Дыры находят и в ядре, и в
OpenSSH; обновление, которое некому поставить, не защищает:

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

**Бан за перебор.** `fail2ban` читает журнал SSH и банит адрес после
нескольких неудачных попыток:

```bash
sudo apt install fail2ban
sudo systemctl enable --now fail2ban
```

Правило для nginx заводить не обязательно: отказы отдаёт сам nginx, и в
журнале они видны как 429 и 444 — по ним удобно смотреть, кто именно стучится
(см. [monitoring.md](monitoring.md)).

**Образы Docker.** `./deploy.sh` пересобирает их из свежих базовых образов.
Если сервер долго не обновлялся, стоит запустить развёртывание хотя бы ради
этого.

## Заголовки безопасности

`nginx/snippets/site.conf` выставляет `X-Content-Type-Options`,
`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` и
`Content-Security-Policy`; в контуре `tls` добавляется `Strict-Transport-Security`.

CSP строгая: страница не загружает ничего со сторонних доменов — весь код
попадает в бандл, шрифты лежат в `frontend/public/fonts` и отдаются с того же
origin. Единственное исключение — `img-src` для тайлов OpenStreetMap на карте
догадки. Если меняете фронтенд и
добавляете внешний ресурс, политику придётся расширить осознанно.

Директива `http2 on` требует nginx 1.25.1 и новее; в `nginx:alpine` он новее.
Оба контура слушают только IPv4: наружу порты публикует Docker, он же
принимает IPv6-соединения хоста, а внутри контейнера IPv6 обычно выключен и
`listen [::]` уронил бы nginx на старте.

## Провайдер спутниковых снимков

По умолчанию используется ESRI World Imagery, токен не нужен. Адрес задаётся
переменной `SATELLITE_TILE_URL` и меняется без пересборки.

Важно: бэкенд **проксирует** тайлы — иначе клиент узнал бы координаты цели.
Перед сменой провайдера или выходом за рамки личного использования проверьте
его условия: проксирование и кэширование тайлов разрешено не всеми. Для
Mapbox шаблон выглядит так (токен подставьте свой):

```
SATELLITE_TILE_URL=https://api.mapbox.com/v4/mapbox.satellite/{z}/{x}/{y}@2x.jpg90?access_token=ВАШ_ТОКЕН
```

## Сколько чего расходуется

| Служба     | Память  | Заметки                                        |
|------------|---------|------------------------------------------------|
| `backend`  | до 1,5 ГБ | четыре воркера, предел задан в docker-compose |
| `postgres` | ~700 МБ | `shared_buffers` 512 МБ                        |
| `redis`    | до 512 МБ | кэш тайлов и счётчики показателей             |
| мониторинг | ~600 МБ | пять служб, выключается `MONITORING=false`      |

Пул соединений считается на процесс: по пять постоянных и пять запасных на
воркер, всего до сорока при сотне разрешённых в PostgreSQL. Запас нужен
миграциям и `psql` руками.

Во время развёртывания к этому добавляется сборка фронтенда — ещё около
гигабайта на несколько минут. На четырёх гигабайтах это проходит, на двух
с включённым мониторингом — уже нет.

## Наблюдаемость

Каждый ответ несёт заголовок `X-Request-ID`. Значение придумывает nginx,
передаёт бэкенду, и оно же стоит в каждой строке лога этого запроса — по
жалобе игрока найти нужное место в логах обоих можно по одному числу.

`GET /api/metrics` отдаёт показатели процесса в формате Prometheus: количество
и время запросов по маршрутам, попадания и промахи кэша тайлов, события партий.
Наружу этот путь закрыт в nginx — снимать его нужно изнутри контура.

В проде логи пишутся объектом JSON (`LOG_FORMAT=json`), чтобы сборщик разбирал
поля сам. Локально формат остаётся человеческим.

Панели, хранение показателей и логов, тревоги — в
[monitoring.md](monitoring.md).

## Резервное копирование

Копия базы снимается каждую ночь таймером systemd и тут же проверяется:
скрипт разворачивает её в отдельную базу и считает в ней игроков. Копия,
которую ни разу не разворачивали, — это не копия, а надежда.

Лежат копии в `/opt/location_king/backups`, хранятся неделю. Кэш тайлов и
счётчики в Redis не выгружаются: тайлы восстановятся сами, а обрыв в графиках
не стоит места на диске.

```bash
systemctl status location-king-backup.timer   # включён ли таймер
journalctl -u location-king-backup --since '3 days ago'
./backup.sh --check                           # снять копию прямо сейчас
```

### Как восстановиться

```bash
cd /opt/location_king
docker compose stop backend

gzip -dc backups/location_king-2026-08-28-0130.sql.gz \
    | docker compose exec -T postgres psql -U locationking -d location_king

docker compose start backend
```

Дамп снимается с ключом `--clean`, поэтому разворачивается поверх существующей
базы: сначала сносит её объекты, потом создаёт заново. Останавливать бэкенд
нужно именно поэтому — иначе он будет обращаться к таблицам, которых в этот
момент нет.

**Копии лежат на том же диске, что и база.** От случайного `DROP TABLE` они
спасут, от смерти диска — нет. Если игра станет важной, копии стоит увозить
наружу: тот же скрипт плюс `rclone` или `scp` в другое место.
